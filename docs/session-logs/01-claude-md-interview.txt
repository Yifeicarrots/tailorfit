  Question 2 of ~8: architecture

  How should the server-side code be organized? Here's my proposal; correct
  anything that's off:

  - Claude calls run in Server Actions (not Route Handlers), so the API key and
    Supabase service logic never reach the client.
  - Pipeline code lives in plain TypeScript modules under lib/ (e.g.
    lib/pipeline/experienceSelector.ts, lib/pipeline/resumeRewriter.ts,
    lib/pipeline/validate.ts). These modules don't import from Next.js, which
    keeps them easy to unit-test.

    instead of importing a singleton, so tests can pass in a mock. Data-access
    functions receive the Supabase client the same way.
  - Validation failures: if a response fails Zod parsing or the no-invention
    checks, retry once, then show the user an error. Never pass partially valid
    output through.

  Actions vs. Route Handlers?
